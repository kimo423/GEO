==================================================
11. 余额算法：本 App 最重要逻辑
==================================================

不要把：

balanceAfterTransaction

作为一个永远不更新的固定值直接写死进每条记录。

因为用户以后可能：

补录旧账

编辑旧账

删除旧账

修改交易日期

这些都会影响后续余额。

正确方案：

按照全历史交易排序后动态累计余额。

全局正序：

transactionDate ASC

createdAtMillis ASC

id ASC

逐笔：

如果：

INCOME

balance += amountCents

如果：

EXPENSE

balance -= amountCents

得到：

balanceAfterTransaction

14. 同一天多笔交易的稳定顺序
==================================================

业务日期只记录：

年月日

无需用户输入具体小时分钟。

因此：

transactionDate

负责业务日期。

同一天的先后顺序：

createdAtMillis

再使用：

id

作为最终稳定 tie-break。

正序：

transactionDate ASC
createdAtMillis ASC
id ASC

UI 账单通常倒序：

transactionDate DESC
createdAtMillis DESC
id DESC

但：

balanceAfterTransaction

必须根据正序流水计算。

App 重启后排序不能随机变化。

27. 期末余额语义：重点
==================================================

期末余额绝对不是：

当前筛选区间收入 - 支出

而是：

从整个账本最早交易开始，

一直累计到：

当前筛选结束日期

得到的全局账户余额。

例如：

8月31日以前已经有：

¥10,000

9月：

收入 ¥5000

支出 ¥1000

则：

9月净变化：

+¥4000

9月期末余额：

¥14,000

不能显示：

¥4,000
